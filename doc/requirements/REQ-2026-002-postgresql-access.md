## 2. 摘要与目标

### 2.1 摘要

当前服务没有数据库连接能力，Demo 只是脚手架示例，不能代表持久化方案。本次接入 PostgreSQL：应用能按配置建立连接，用 `/ready` 探测数据库是否可达，并删除 Demo 示例接口。本迭代不创建业务表，不把 LLM 档案或对话写入数据库。

### 2.2 需求目标

1. 应用能从配置读取 PostgreSQL 连接信息，并在进程内提供可注入的数据库 Session。
2. 调用方可通过就绪探针判断数据库是否可达；活性探针保持原语义，不因数据库故障把进程判死。
3. 删除 `/api/v1/demo` 示例接口及其内存存储，避免把示例 CRUD 误当作业务或落库方案。
4. 未配置 LLM 密钥、或数据库进程未启动时，服务仍可启动；`/` 与 `/health` 仍可用。
5. 不创建业务表、不迁移历史数据、不把 LLM 配置接入数据库。

### 2.3 非目标

- 不创建任何业务表（含 Demo 表、LLM 档案表、会话表、审计表）。
- 不提供档案、对话或其他业务实体的增删改 API。
- 不把 LLM 密钥、模型档案或聊天记录写入数据库。
- 不引入认证、权限、租户隔离、审计、脱敏。
- 不引入 Alembic 自动迁移，不在启动时对数据库执行建表。
- 不把 SQLite 或其他数据库当作 PostgreSQL 的替代实现。

| US-002 | Must | 作为运维/调用方，我希望活性探针与就绪探针分开，以便数据库故障时不必重启进程。 | 编排系统分别探测 `/health` 与 `/ready` | US-001 |
| US-003 | Must | 作为维护者，我希望删除 Demo 示例接口，以免后续把它当成需要落库的业务。 | 调用原 `/api/v1/demo` 应不再提供该能力 | 无 |
| US-004 | Must | 作为后续维护者，我希望本迭代不建表，以便第一张业务表可以单独立项并走完整数据库设计。 | 检查仓库无业务 DDL、无占位列 | US-001 |

### 3.2 范围内

- 确认数据库产品为 PostgreSQL，建议版本 16。
- 增加数据库连接配置，示例只出现在 `.env.example` 与本地 Compose，不含真实密钥。
- 提供 SQLAlchemy 引擎、Session 依赖和进程结束时的引擎释放。
- 新增 `GET /ready`：数据库可达返回成功，不可达返回 503，响应不包含连接串。
- 保持 `GET /health` 现有契约，不探测数据库。
- 删除 Demo 路由、Schema、内存存储和对应测试。
- 默认 pytest 不连接真实 PostgreSQL；真实连通性作为环境限制项。

### 3.3 范围外

- 业务表、索引、初始化数据、升级/回滚 DDL：无业务实体，不写空脚本。
- LLM 档案落库、档案 CRUD、密钥入库：仍由后续独立需求处理。
- 会话记忆、聊天历史、向量库。
- 认证、租户、审计、脱敏、缓存。
- 生产级高可用、读写分离、连接池精细调参。

## 4. 业务流程

### 4.1 流程说明

- 前置条件：应用已配置 PostgreSQL 连接 URL。数据库进程不是进程启动的前置条件。
- 触发入口：进程启动（建立引擎，不强制连库）；`GET /ready`（探测数据库）；`GET /health`（不探库）。
- 最终结果：配置合法即可启动。`/health` 只表示进程活着。`/ready` 成功表示当时可以执行 `SELECT 1`；失败不改变任何数据。

1. 应用读取 `DATABASE_URL` 并创建引擎。
2. 调用方访问 `/health` 时不访问数据库，按原契约返回。
3. 调用方访问 `/ready` 时执行一次连通性检查。
4. 检查成功则返回就绪；失败则返回 503，不泄露连接信息。

### 4.2 业务流程图

~~~mermaid
flowchart TD
    A([开始]) --> B[应用读取数据库配置并创建引擎]
    B --> C{调用方请求类型}
    C -- GET /health --> D[不访问数据库]
    D --> E[返回原活性契约]
    E --> Z([结束])
    C -- GET /ready --> F[执行 SELECT 1]
    F --> G{数据库可达?}
    G -- 是 --> H[返回就绪成功]
    H --> Z
    G -- 否 --> I[返回 503 且不泄露连接串]
    I --> Z
~~~

### 4.3 异常与替代流程

| 编号 | 触发条件 | 系统行为 | 用户提示 | 数据是否改变 |
| --- | --- | --- | --- | :---: |
| EX-001 | 数据库进程未启动或网络不可达 | `/ready` 返回 503；`/health` 仍成功 | 仅表明数据库不可用，不含连接串 | 否 |
| EX-002 | 连接配置缺失或非法 | 应用启动失败或配置校验失败 | 配置错误，不输出完整连接串 | 否 |
| EX-003 | 调用已删除的 `/api/v1/demo` | 按框架默认返回不存在 | 404 | 否 |
| EX-004 | 未配置 LLM 密钥 | `/`、`/health`、`/ready` 不因缺密钥失败 | 与 LLM 无关 | 否 |

## 5. 功能需求与验收标准

### 5.1 REQ-001 数据库连接配置与 Session

#### 5.1.1 需求说明

- 关联用户故事：`US-001`
- 优先级：Must
- 触发入口：应用启动、后续通过依赖注入获取 Session
- 前置条件：无
- 输入：`DATABASE_URL` 配置
- 处理规则：
  1. 连接信息只来自配置，不写进代码常量以外的本地示例默认值说明，且不得把真实凭据提交进仓库。
  2. 应用提供可注入的数据库 Session，供后续需求复用；本迭代没有任何业务写入。
  3. 进程结束时释放引擎连接池。
  4. 创建引擎不等于探测成功；启动阶段不得因为数据库进程未启动而拒绝提供 `/health`。
- 输出：可用于执行 SQL 的 Session 边界
- 限制：本迭代不创建表，不在启动时执行 DDL

#### 5.1.2 验收标准

- `AC-001`：Given 配置了合法 `DATABASE_URL`，When 启动应用，Then 应用能完成启动，且存在可注入的数据库 Session 入口。
- `AC-002`：Given 数据库进程未启动，When 启动应用并访问 `/health`，Then 进程可启动且 `/health` 仍返回成功。

### 5.2 REQ-002 就绪探针

#### 5.2.1 需求说明

- 关联用户故事：`US-002`
- 优先级：Must
- 触发入口：`GET /ready`
- 前置条件：应用已启动
- 输入：无业务参数
- 处理规则：
  1. 就绪探针探测 PostgreSQL 是否可执行 `SELECT 1`。
  2. 可达时返回成功，响应包含可观察的数据库就绪状态。
  3. 不可达时返回 503，响应可区分“进程活着但数据库不可用”，且不得包含连接串、账号或密码。
  4. `/ready` 不写数据。
- 输出：就绪成功或 503
- 限制：日志不得记录完整连接串或密码

#### 5.2.2 验收标准

- `AC-003`：Given 数据库可达，When 访问 `GET /ready`，Then 返回 200，且响应标明数据库就绪。
- `AC-004`：Given 数据库不可达，When 访问 `GET /ready`，Then 返回 503，响应标明数据库不可用，且正文和常规日志不含连接串或密码。

### 5.3 REQ-003 活性探针保持不变

#### 5.3.1 需求说明

- 关联用户故事：`US-002`
- 优先级：Must
- 触发入口：`GET /health`
- 前置条件：应用已启动
- 输入：无
- 处理规则：
  1. `/health` 继续表示进程活性，不探测数据库。
  2. 响应字段保持现有契约，不新增数据库状态字段。
- 输出：与接入前相同的健康检查响应
- 限制：不得把 `/health` 改成就绪探针

#### 5.3.2 验收标准

- `AC-005`：Given 应用已启动且数据库不可达，When 访问 `GET /health`，Then 返回 200，`status` 为 `ok`，且响应不含数据库状态字段。

### 5.4 REQ-004 删除 Demo 示例接口

#### 5.4.1 需求说明

- 关联用户故事：`US-003`
- 优先级：Must
- 触发入口：原 `/api/v1/demo` 系列路径
- 前置条件：无
- 输入：原 Demo 请求
- 处理规则：
  1. 删除 Demo 路由、请求/响应模型、进程内存储和专用测试。
  2. 不再提供 Demo 列表、详情、创建能力。
  3. 不得把 Demo 改造成数据库表后继续保留。
- 输出：原 Demo 路径不再作为产品接口存在
- 限制：不得影响 `/`、`/health`、`/ready` 与 `/api/v1/llm/*`

#### 5.4.2 验收标准

- `AC-006`：Given 服务已启动，When 访问 `GET /api/v1/demo` 或 `POST /api/v1/demo`，Then 系统不再返回原 Demo 列表或创建成功契约。
- `AC-007`：Given 仓库当前代码，When 检查路由与测试，Then 不存在 Demo 内存存储复位入口，也不存在 Demo 表。

### 5.5 REQ-005 本迭代不建业务表

#### 5.5.1 需求说明

- 关联用户故事：`US-004`
- 优先级：Must
- 触发入口：仓库 SQL、模型与启动流程
- 前置条件：无
- 输入：无
- 处理规则：
  1. 不新增业务表、占位列、表前缀、租户字段、软删除字段或雪花主键。
  2. 不在 `doc/sql` 写入无对象的空 DDL 充数。
  3. 后续第一张业务表必须单独立项并补充数据库设计。
- 输出：连接层可用，数据模型仍为空
- 限制：禁止为未确认业务预建表

#### 5.5.2 验收标准

- `AC-008`：Given 本迭代交付范围，When 检查 `doc/sql`、应用模型和启动流程，Then 不存在新建业务表的 DDL，启动时也不执行建表。

### 5.6 REQ-006 安全底线与 LLM 隔离

#### 5.6.1 需求说明

- 关联用户故事：`US-001`
- 优先级：Must
- 触发入口：配置、探针、日志、LLM 接口
- 前置条件：无
- 输入：数据库配置、LLM 配置
- 处理规则：
  1. 真实连接凭据不得写入仓库文档或示例以外的代码。
  2. 响应和常规日志不得输出连接串、密码、LLM 密钥。
  3. LLM 接口仍从应用配置读取档案，不访问数据库。
  4. 未配置 LLM 密钥时，`/`、`/health` 仍可用。
- 输出：数据库接入不影响 LLM 现有契约
- 限制：不建设审计或脱敏功能

#### 5.6.2 验收标准

- `AC-009`：Given 未配置 LLM 密钥，When 访问 `/` 与 `/health`，Then 二者成功且不访问模型上游。
- `AC-010`：Given `/ready` 成功或失败，When 检查响应体，Then 不出现连接串、用户名密码或 `api_key` 字段。

## 6. 业务规则与状态

### 6.1 业务规则

| 规则编号 | 规则 | 适用范围 | 违反时行为 |

| BR-001 | `/health` 不探测数据库 | 活性探针 | 发现探库视为超出范围 |

### 6.2 状态与迁移

不适用。本需求不引入可持久化业务实体或业务状态机。`/ready` 的数据库状态只表示当时探测结果，不是可迁移的业务状态。
