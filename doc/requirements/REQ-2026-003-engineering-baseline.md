## 2. 摘要与目标

### 2.1 摘要

当前服务已有 LLM 与 PostgreSQL 接入，但代码风格靠人工，JSON 错误形状不统一，日志不能按环境打印请求入参和响应。本次补齐 FastAPI 项目最小工程基线：用 Ruff 统一检查和格式化；把 JSON 接口的校验失败、领域错误、框架 HTTP 错误和未捕获异常收成同一套失败出口；并提供可开关的请求/响应日志，开发可打开、生产默认可关闭。成功响应形状、探针契约和 SSE 事件协议保持不变，不引入 `{code, message, data}` 成功信封。

### 2.2 需求目标

1. 开发者可用项目约定命令检查并格式化 Python 代码，不必并行维护多套风格工具。
2. JSON 接口的失败响应统一为 HTTP 状态码 + `detail.code` / `detail.message`，调用方用同一套字段识别原因。
3. 未捕获异常返回泛化 500，不把堆栈、密钥、连接串写进响应。
4. 应用日志级别可配；另有独立开关控制是否打印请求入参和响应，默认关闭。
5. `/`、`/health`、`/ready` 以及现有 `/api/v1/llm/*` 成功体、已发布业务错误码和 SSE 事件保持兼容。

### 2.3 非目标

- 不把成功和失败都包成 `{code, message, data}` 或其他成功响应信封。
- 不改变 `/health`、`/ready` 的探针响应模型，不把探针失败改写成 `detail.code`。
- 不把已开始的 SSE 流中失败改写成普通 JSON；流中失败仍使用 `event: error`。
- 不引入认证、权限、审计、脱敏产品、请求 ID 平台、链路追踪、指标采集、限流或 CI 流水线。
- 不引入 mypy/ty 类型检查、pre-commit、Alembic、CORS、Dockerfile 作为本需求交付物。
- 不建设通用 CRUD、Service 基类、DI 容器或用于改写成功体的全局拦截中间件。
- 不把访问日志落成审计表或对外查询接口。
- 不新增业务接口、数据表或 LLM 编排行为。

### 3.2 范围内

- 将 Ruff 作为本仓库唯一的 Python lint 与格式化工具，提供可重复执行的检查命令。
- 本迭代交付时，仓库内受管 Python 代码应能通过该检查与格式化检查。
- JSON 接口失败统一为 HTTP 状态码 + `{"detail": {"code": "...", "message": "..."}}`，覆盖：
  - Schema/请求校验失败
  - 已知领域错误（当前为 LLM）
  - 框架 HTTP 错误（如未找到的业务路径）
  - 未捕获异常
- 当前 LLM 已发布错误码与 HTTP 状态保持不变。
- 未捕获异常返回 500，泛化 `code`/`message`，响应不含堆栈和密钥。
- 应用日志级别可配置。
- 新增独立的请求/响应日志开关：打开时打印请求入参和响应；关闭时不打印业务正文；默认关闭。
- 更新开发者可发现的命令与配置说明。

### 3.3 范围外

- 统一成功响应包装、把成功 HTTP 状态改成永远 200。
- GitHub Actions 或其他 CI、pre-commit hook、类型检查器。
- 审计、脱敏产品、权限、登录。
- 结构化 JSON 日志平台、集中式日志采集、OpenTelemetry、Prometheus。
- 数据库、新 HTTP 业务接口、LLM 编排规则变更。

## 4. 业务流程

### 4.1 流程说明

- 前置条件：应用已启动；开发者工作区已安装项目开发依赖。
- 触发入口：开发者执行代码检查命令；调用方访问现有 HTTP 接口。
- 最终结果：风格问题在检查阶段被发现；JSON 失败有统一 `code`/`message`；探针和 SSE 仍按原契约工作；请求/响应正文仅在开关打开时打印，且始终遮蔽密钥类字段。

1. 开发者对仓库执行 Ruff 检查/格式化，受管 Python 文件通过。
2. 调用方访问 HTTP 接口。
3. 若为 `/health` 或 `/ready`，返回原探针模型，且不因访问日志开关打印探针正文。
4. 若 JSON 请求校验失败、领域错误、框架 HTTP 错误或未捕获异常，返回对应 HTTP 状态和统一 `detail.code`/`detail.message`。
5. 若 SSE 已开始生成后失败，发送 `event: error`，事件数据仍含 `code`/`message`。
6. 若请求/响应日志开关打开，则记录该方法的请求入参和响应（SSE 不逐条记录 delta）；开关关闭则不记录业务正文。

### 4.2 业务流程图

~~~mermaid
flowchart TD
    A([开始]) --> B{入口}
    B -- 开发者检查代码 --> C[执行项目约定的 Ruff 检查与格式化]
    C --> D{受管 Python 通过?}
    D -- 否 --> E[报告违规且不改变运行时契约]
    E --> Z([结束])
    D -- 是 --> F[检查通过]
    F --> Z
    B -- HTTP 请求 --> G{接口类型}
    G -- 探针 /health /ready --> H[保持原探针响应]
    H --> I[不打印探针请求响应正文]
    I --> Z
    G -- SSE 已开始生成 --> J{流中失败?}
    J -- 是 --> K[发送 event: error 后结束流]
    K --> L{访问日志开关打开?}
    L -- 是 --> M[记录请求入参，不逐条记录 delta]
    M --> Z
    L -- 否 --> Z
    J -- 否 --> N[按原 SSE 事件完成]
    N --> L
    G -- JSON 接口 --> O{失败?}
    O -- 校验失败 --> P[422 + detail.code/message]
    P --> Q{访问日志开关打开?}
    Q -- 是 --> R[记录请求入参和响应]
    R --> Z
    Q -- 否 --> Z
    O -- 领域或框架 HTTP 错误 --> S[对应状态 + detail.code/message]
    S --> Q
    O -- 未捕获异常 --> T[500 + 泛化 code/message]
    T --> Q
    O -- 否 --> U[返回原成功资源模型]
    U --> Q
~~~

## 5. 功能需求与验收标准

### 5.1 REQ-001 使用 Ruff 统一检查与格式化

#### 5.1.1 需求说明

- 关联用户故事：`US-001`
- 优先级：Must
- 触发入口：仓库开发依赖与约定命令
- 前置条件：已安装项目开发依赖
- 输入：仓库内受管 Python 源码
- 处理规则：
  1. 本仓库以 Ruff 作为 Python lint 和格式化的唯一标准工具，不再并行引入 Black、isort、flake8 作为同类工具。
  2. 检查规则和格式化配置纳入版本库，开发者不必依赖个人 IDE 默认值。
  3. 仓库文档提供可复制的检查命令；本迭代不要求建设 CI。
  4. 交付时 `app/`、`tests/` 等受管 Python 代码必须通过检查和格式化检查。
  5. 不把 `.venv/`、缓存和生成物纳入检查范围。
- 输出：可重复的代码检查入口，以及通过检查的受管代码
- 限制：不得借格式化之机关闭业务错误检查；不得把类型检查器纳入本需求

#### 5.1.2 验收标准

- `AC-001`：Given 已安装开发依赖，When 执行仓库文档中的 Ruff 检查命令，Then 命令可用且对受管 Python 代码以非零状态报告违规、以零状态表示通过。
- `AC-002`：Given 本迭代交付的工作区，When 对受管 Python 代码执行检查与格式化检查，Then 二者均通过。
- `AC-003`：Given 仓库依赖声明，When 检查开发依赖，Then 存在 Ruff，且不存在并列的 Black/isort/flake8 作为项目标准工具。

### 5.2 REQ-002 JSON 失败统一为 code/message

#### 5.2.1 需求说明

- 关联用户故事：`US-002`、`US-005`
- 优先级：Must
- 触发入口：现有 JSON 业务接口及会返回 JSON 错误的校验阶段
- 前置条件：应用已启动
- 输入：非法请求、会触发已发布领域错误的请求、不存在的业务路径
- 处理规则：
  1. JSON 失败必须使用 HTTP 状态码 + `{"detail": {"code": "<稳定码>", "message": "<说明>"}}`。
  2. `detail` 可以增加字段级错误等附加信息，但 `code` 与 `message` 必须存在且为字符串。
  3. 现有 LLM 错误语义保持不变：

     | HTTP | `detail.code` |
     | --- | --- |
     | 422 | `validation_error` |
     | 404 | `profile_not_found` |
     | 503 | `profile_not_ready` |
     | 503 | `upstream_timeout` |
     | 503 | `upstream_failed` |

  4. Schema/请求校验失败也使用 `validation_error`，不再对调用方暴露 FastAPI 默认的 `detail` 数组作为唯一形状。
  5. 未捕获异常使用稳定码 `internal_error`，见 REQ-003。
  6. 其他 JSON HTTP 错误（例如业务路径不存在）也必须带 `code` 与 `message`，不得只返回字符串 `detail`。
  7. 成功响应继续返回原资源模型，不得包一层 `data`。
  8. 失败转换必须稳定，不得每个路由手写互不一致的失败体。
  9. message 不得包含密钥、连接串或堆栈。
- 输出：统一形状的 JSON 错误
- 限制：不改变成功体；不把该出口套到探针成功/失败模型上

#### 5.2.2 验收标准

- `AC-004`：Given 请求指定不存在的档案，When 调用 `POST /api/v1/llm/chat`，Then 返回 404，且 `detail` 含 `code=profile_not_found` 与 `message` 字符串。
- `AC-005`：Given 主档案上游失败且无可用备用，When 调用同步对话接口，Then 返回 503，且 `detail.code` 为现有的 `upstream_timeout` 或 `upstream_failed`。
- `AC-006`：Given 对话成功，When 检查响应 JSON，Then 顶层仍为 `profile`/`content`/`usage`，不存在统一信封字段 `data` 或业务 `code`。
- `AC-011`：Given 请求体缺少必填 `messages`，When 调用同步对话接口，Then 返回 422，且 `detail` 为对象，`code=validation_error`，并存在 `message`。

### 5.3 REQ-003 未捕获异常的泛化 500

#### 5.3.1 需求说明

- 关联用户故事：`US-003`
- 优先级：Must
- 触发入口：JSON 业务接口出现未声明异常
- 前置条件：应用已启动
- 输入：会触发未捕获异常的请求（测试中用可控方式注入）
- 处理规则：
  1. 返回 HTTP 500。
  2. 响应 `detail` 为对象：`code=internal_error`，`message` 为泛化中文或中性说明。
  3. 无论调试开关是否开启，响应正文都不得包含堆栈、异常类名、密钥或连接串。
  4. 系统必须记录该失败，日志中允许出现异常类型，禁止出现密钥明文。
- 输出：泛化 500 JSON
- 限制：不得把未捕获异常伪装成 200；不得改变探针在数据库失败时的 503 行为

#### 5.3.2 验收标准

- `AC-007`：Given JSON 业务接口抛出未声明异常，When 调用该接口，Then 返回 500，且 `detail.code` 为 `internal_error`，`detail.message` 为泛化文案。
- `AC-008`：Given 同上请求，When 检查响应正文，Then 不含 traceback、密钥或连接串。
- `AC-009`：Given 调试配置开启，When 再次触发未声明异常，Then 响应正文仍不含堆栈。

### 5.4 REQ-004 探针和 SSE 保持原契约

#### 5.4.1 需求说明

- 关联用户故事：`US-005`
- 优先级：Must
- 触发入口：`GET /health`、`GET /ready`、`POST /api/v1/llm/chat/stream`
- 前置条件：应用已启动
- 输入：探针请求、可触发流中失败的流式请求
- 处理规则：
  1. `/health` 继续返回原活性模型。
  2. `/ready` 数据库不可达时继续 503，正文仍为就绪模型，不得改成 `detail.code`。
  3. 流式接口在校验失败时返回普通 JSON 统一错误；生成开始后的失败仍发 `event: error`，且不得再发 `done`。
  4. SSE `event: error` 的数据仍含 `code` 与 `message`，与 JSON 失败字段对齐。
  5. `GET /` 保持现有欢迎信息结构。
- 输出：探针与 SSE 的原可观察契约
- 限制：禁止用成功响应包装器覆盖这些入口

#### 5.4.2 验收标准

- `AC-010`：Given 数据库不可达，When 访问 `GET /ready`，Then 返回 503，正文含 `status` 与 `database`，且没有 `detail.code`。
- `AC-012`：Given 流式生成中途失败，When 读取 SSE，Then 最后有效事件名为 `error`，数据含 `code` 与 `message`，且没有随后的 `done`。
- `AC-013`：Given 应用已启动，When 访问 `GET /health` 与 `GET /`，Then 分别保持原 200 契约。

### 5.5 REQ-005 应用日志级别与敏感信息底线

#### 5.5.1 需求说明

- 关联用户故事：`US-004`
- 优先级：Must
- 触发入口：应用启动、领域错误、未捕获异常
- 前置条件：无
- 输入：日志级别配置、失败请求
- 处理规则：
  1. 应用日志级别可配置；更详细级别只增加排障信息，不降低密钥禁令。
  2. 已知领域错误日志允许：档案名、错误码、异常类型；未捕获异常日志允许异常类型。
  3. 任何日志开关组合下，禁止明文记录：密码、Token、密钥、连接串、Authorization。
  4. 本需求不建设审计功能或脱敏产品；遮蔽密钥属于安全底线，不是独立脱敏模块。
  5. 不强制改为 JSON 日志，不引入外部日志平台。
- 输出：可配置的应用日志，失败路径可观察且无密钥明文
- 限制：日志配置不得要求新的外部依赖服务

#### 5.5.2 验收标准

- `AC-014`：Given 访问日志开关关闭且触发已知 LLM 领域错误，When 查看应用日志，Then 能观察到错误码或异常类型，且不含 `api_key`、连接串和对话 messages 正文。
- `AC-015`：Given 触发未捕获异常，When 查看应用日志，Then 能观察到异常类型，且 HTTP 正文不含堆栈、不含密钥。
- `AC-016`：Given 以非调试级别且访问日志关闭启动，Then 应用仍能启动，且 `/health` 可用。

### 5.6 REQ-006 可开关的请求入参与响应日志

#### 5.6.1 需求说明

- 关联用户故事：`US-006`
- 优先级：Must
- 触发入口：应用配置、任意 HTTP 请求
- 前置条件：应用已启动
- 输入：独立于日志级别的布尔开关、HTTP 请求与响应
- 处理规则：
  1. 提供独立配置开关，开发和生产都能通过配置打开或关闭，不必改代码。
  2. 默认关闭。未配置时等同关闭。
  3. 开关关闭时：不打印请求体、查询业务入参和响应体。
  4. 开关打开时：打印请求方法、路径、入参（查询/路径/JSON 体）和响应状态与响应体，便于对照一次调用。
  5. 打开时仍必须遮蔽密码、Token、密钥、连接串、Authorization 等明文；不得因为打开开关而把密钥打进日志。
  6. `/health`、`/ready` 即使开关打开也不打印请求/响应正文，避免探针刷屏。
  7. SSE 打开开关时只记录请求入参和“流式响应已开始/结束或失败”，不逐条记录 `delta` 文本。
  8. 过长正文必须截断。
  9. 该开关不等于审计：不落库、不提供查询接口、不新增权限项。
  10. 该开关与日志级别相互独立：级别用于控制详细程度，开关专门控制是否打印 HTTP 入参和返回。
- 输出：可在 `.env.example` 中发现的开关；打开时可观察入参和返回，关闭时无业务正文
- 限制：不得默认在生产打开；不得记录被遮蔽字段的明文

#### 5.6.2 验收标准

- `AC-017`：Given 开关关闭或未配置，When 调用 `POST /api/v1/llm/chat` 并提交消息，Then 应用日志不含该消息正文和助手响应正文。
- `AC-018`：Given 开关打开，When 调用同步对话接口，Then 日志能观察到 HTTP 方法、路径、请求入参和响应体中的助手文本或明确截断标记。
- `AC-019`：Given 开关打开且请求带 Authorization 或档案密钥配置存在，When 发生一次 JSON 调用，Then 日志中不出现密钥或 Authorization 明文。
- `AC-020`：Given 开关打开，When 访问 `/health` 或 `/ready`，Then 日志不出现探针响应正文。
- `AC-021`：Given 开关打开，When 调用流式对话并产生多段 `delta`，Then 日志不包含每一段增量文本的完整逐条记录。
- `AC-022`：Given `.env.example`，When 查看配置说明，Then 能找到该开关，并标明默认关闭及开发/生产均可配置。

## 6. 业务规则与状态

### 6.1 业务规则

| 规则编号 | 规则 | 适用范围 | 违反时行为 |
| --- | --- | --- | --- |
| BR-001 | 成功响应使用资源模型，不使用统一信封 | 全部 JSON 成功响应 | 视为破坏兼容，不得验收 |
| BR-002 | JSON 失败使用 HTTP 状态 + `detail.code`/`detail.message` | JSON 校验、领域、框架 HTTP、未捕获异常 | 不得改为 200 + 业务码，不得只返回字符串 `detail` |
| BR-003 | Schema 校验失败也使用统一对象，`code=validation_error` | 请求校验 422 | 不得再以数组 `detail` 作为唯一对外形状 |
| BR-004 | 探针失败保持原模型，不进入 JSON 错误出口 | `/health`、`/ready` | 不得输出 `detail.code` 替代探针字段 |
| BR-005 | SSE 流中失败走事件，不走 JSON 失败出口 | `/api/v1/llm/chat/stream` 生成阶段 | 不得把流改成 `application/json` |
| BR-006 | 现有 LLM 错误码与 HTTP 状态不得改名或改状态 | LLM JSON 失败 | 视为不兼容 |
| BR-007 | 密钥、连接串、Authorization 在任何开关下都不得明文进响应和日志 | 错误出口与日志 | 必须修复后才能验收 |
| BR-008 | 本需求不建设审计或脱敏产品 | 全范围 | 不得新增审计表、审计接口或脱敏流程 |
| BR-009 | Ruff 是唯一 Python 风格标准工具 | 开发工具链 | 不得再引入并列格式化/lint 工具 |
| BR-010 | 请求/响应正文只在访问日志开关打开时打印，默认关闭 | HTTP 访问日志 | 关闭时打印业务正文视为缺陷 |
| BR-011 | 探针即使打开开关也不打印正文；SSE 不逐条打印 delta | 访问日志 | 刷屏或逐 token 落日志视为缺陷 |

### 6.2 状态与迁移

不适用。本需求不引入业务实体或可迁移状态。日志级别、访问日志开关和检查通过/失败只是运行与交付状态，不是业务状态机。

访问日志开关：

| 状态 | 含义 | 允许操作 | 可迁移到 |
| --- | --- | --- | --- |
| 关闭（默认） | 不打印请求/响应正文 | 正常提供 API | 打开 |
| 打开 | 打印入参和返回（受遮蔽、截断和探针/SSE 规则约束） | 正常提供 API | 关闭 |

该状态来自配置，不是资源工作流。
